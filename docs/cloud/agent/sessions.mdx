A **session** holds the agent's conversation and can reuse its live browser.
One session ID can contain multiple runs. Every run creates a session implicitly
unless you pass an existing session ID.

Pass `session_id` / `sessionId` to continue:

<CodeGroup>
```python Python
first = client.runs.create("Open Hacker News")
client.runs.wait_for_completion(first.id)

follow_up = client.runs.create(
    "Now summarize the top story",
    session_id=first.session_id,
)
result = client.runs.wait_for_completion(follow_up.id)
print(result.result)
```
```typescript TypeScript
const first = await client.runs.create({
  task: "Open Hacker News",
  model: "gpt-5.6-luna",
  modelParams: { reasoning: { effort: "xhigh" } },
});
await client.runs.waitForCompletion(first.id);

const followUp = await client.runs.create({
  task: "Now summarize the top story",
  model: "gpt-5.6-luna",
  modelParams: { reasoning: { effort: "xhigh" } },
  sessionId: first.sessionId,
});
const result = await client.runs.waitForCompletion(followUp.id);
console.log(result.result);
```
</CodeGroup>

Omit the session ID for a new conversation. Pass only a [workspace
ID](/cloud/agent/workspaces) when you want a fresh conversation that keeps the
same files.

## Set a session budget

<Warning>
The session-wide budget rollout remains pending.
The current production runtime still checks paid budgets per run.
Do not rely on `maxCostUsd` to limit total spending across paid-session follow-ups yet.
This section describes the behavior after the coordinated rollout.
</Warning>

After the rollout, `maxCostUsd` sets the total budget for the session, including its previous runs.
It does not give each follow-up a new budget.
New API sessions default to \$25.

The proposed fix keeps this budget independent of the account balance.
Its release requires a credit check during execution first.
All sessions in one project share its credits.
Cloud checks available credits when it starts a run.
A top-up adds credits without changing the session budget.

| Request | Budget behavior |
|---|---|
| New run with `maxCostUsd` | Sets the new session's total budget. |
| Follow-up without `maxCostUsd` | Keeps the session's current budget. |
| Follow-up with `maxCostUsd` | Requests a replacement for the session's total budget. |
| PATCH to `/sessions/{session_id}/cost-cap` | Replaces the budget without starting a run. |

Previous recorded spending counts against the budget.
For example, a session with a \$5 budget and \$2 spent has \$3 left.
Changing its budget to \$8 leaves \$6, not \$8.
You can increase or decrease the budget, but the value must exceed zero.
A lower budget does not refund previous spending.

For example, 50 sessions can each have a \$25 budget while sharing \$10 of project credits.
The API does not reserve \$25 for each session.
Running V4 model and search requests do not recheck project credits.
A session can therefore continue after other sessions exhaust the shared credits.

### Start and follow up

These examples assume enough available credits.
Create a session with a \$5 total budget:

```bash
curl --fail-with-body https://api.browser-use.com/api/v4/runs \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"task":"Find three vendors","maxCostUsd":5}'
```

Save the response's `sessionId` as `SESSION_ID`.
Wait for the run to finish before you send this follow-up.
This request raises the total budget to \$8:

```bash
curl --fail-with-body https://api.browser-use.com/api/v4/runs \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"task\":\"Compare their prices\",\"sessionId\":\"$SESSION_ID\",\"maxCostUsd\":8}"
```

Omit `maxCostUsd` to keep the current budget.
In the Python SDK, use `max_cost_usd=5` with `client.runs.create()`.
In the TypeScript SDK, use `maxCostUsd: 5` with `client.runs.create()`.

### Edit the budget without starting a run

PATCH already updates the stored limit while the session runs or stays idle.
After the rollout, that limit controls the total session budget:

```bash
curl --fail-with-body -X PATCH \
  "https://api.browser-use.com/api/v4/sessions/$SESSION_ID/cost-cap" \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"maxCostUsd":8}'
```

The response contains `sessionId` and the new `maxCostUsd` as a decimal string.
This request does not reset spending or restart a stopped run.
Send a follow-up after you raise an exhausted budget.
The budget check uses the updated value for subsequent work.
Work already in progress can finish above the budget.

Queued messages keep the session budget.
The queue request does not support `maxCostUsd`.
Use PATCH to change the budget before you send the next queued message.

<Warning>
Production currently reduces saved budgets when credits run low.
A top-up does not restore those existing budgets.
Use PATCH to replace an affected budget.
The fix preserves existing budgets because it cannot distinguish balance reductions from user choices.
</Warning>

### Read the budget and recorded spending

<Info>
The GET endpoint also awaits the coordinated rollout.
The public API can return `405 Method Not Allowed` until that deployment completes.
</Info>

```bash
curl --fail-with-body \
  "https://api.browser-use.com/api/v4/sessions/$SESSION_ID/cost-cap" \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY"
```

After deployment, this endpoint returns the session budget and recorded spending:

```json
{
  "sessionId": "00000000-0000-0000-0000-000000000000",
  "spentUsd": "2.000000",
  "maxCostUsd": "8.000000",
  "budgetScope": "session"
}
```

The example leaves \$6 of the session budget.
Actual available spending also depends on the account balance.
`spentUsd` reports recorded charges, so unfinished calls can add costs later.
`maxCostUsd` can be `null` for a session without a stored budget.

The planned paid-session budget covers model and web-search charges.
It does not include browser time or proxy traffic.
Read [`GET /sessions/{session_id}/cost`](/cloud/guides/billing#see-what-a-v4-session-cost) for browser and proxy costs.
That cost endpoint reports usage, not the remaining budget.

## Keep the browser open between runs

After a session's last run, its browser stays open about 2 minutes, then
stops. A later follow-up gets a fresh browser with the same settings and
profile, but not the old tabs or page state. Set `keepAlive` on the run to keep
the browser open longer: integer seconds from 120 to 14400 (default 120), never
past the browser's 4-hour lifetime. Follow-ups inherit the value, a new value
changes it, and `null` restores 120 seconds.

<CodeGroup>
```python Python
run = client.runs.create("Open my dashboard", keep_alive=900)
```
```typescript TypeScript
const run = await client.runs.create({
  task: "Open my dashboard",
  keepAlive: 900,
});
```
```bash curl
curl https://api.browser-use.com/api/v4/runs \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"task":"Open my dashboard","keepAlive":900}'
```
</CodeGroup>

SDK 3.12+ types it as `keep_alive` / `keepAlive`. On 3.11.3, Python must pass
`keepAlive=900` (`keep_alive` sends the wrong key) and TypeScript needs
`as RunCreateBody`. Unlike the boolean `keepAlive` in V2/V3, V4 takes seconds
and rejects `true` with 422. Kept time is billed as browser time but takes no
concurrency slot. Free-tier and Zero Data Retention runs always use 120 seconds.

## Follow up while a run is busy

Use the session queue to send the next instruction without interrupting the
active run. The response is a queued message, not a run: its `runId` can be
`null` until dispatch. Keep its message ID and poll that message before waiting
for the resulting run. Do not resend the message to poll it.

<CodeGroup>
```python Python
import time

message = client.sessions.send_message(
    first.session_id,
    "Now summarize the top story",
    interrupt=False,
)
deadline = time.monotonic() + 300
while message.run_id is None:
    if message.status.value in {"cancelled", "superseded", "failed"}:
        raise RuntimeError(f"Queued message {message.status.value}")
    remaining = deadline - time.monotonic()
    if remaining <= 0:
        raise TimeoutError(f"Message {message.id} is still waiting; keep its ID")
    time.sleep(min(1, remaining))
    message = client.sessions.get_message(first.session_id, message.id)

result = client.runs.wait_for_completion(message.run_id)
print(result.status.value, result.result)
```
```typescript TypeScript
let message = await client.sessions.sendMessage(first.sessionId, {
  text: "Now summarize the top story",
  interrupt: false,
});
const deadline = Date.now() + 300_000;
while (message.runId === null) {
  if (["cancelled", "superseded", "failed"].includes(message.status)) {
    throw new Error(`Queued message ${message.status}`);
  }
  const remaining = deadline - Date.now();
  if (remaining <= 0) {
    throw new Error(`Message ${message.id} is still waiting; keep its ID`);
  }
  await new Promise((resolve) => setTimeout(resolve, Math.min(1_000, remaining)));
  message = await client.sessions.getMessage(first.sessionId, message.id);
}

const result = await client.runs.waitForCompletion(message.runId);
console.log(result.status, result.result);
```
</CodeGroup>

This example times out only its local wait. It does not remove the queued
message or cancel a run. `interrupt=True` / `interrupt: true` instead cancels
the active run so the new instruction can run immediately. Keep it false
to preserve the active work.

## Manage a session

### Rename

```bash
curl -X PATCH "https://api.browser-use.com/api/v4/sessions/$SESSION_ID" \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"title": "Q3 vendor research"}'
```

Titles are up to 255 characters. `null` or a blank title clears the name, and
the dashboard shows the opening task instead.

### Delete

```bash
curl -X DELETE "https://api.browser-use.com/api/v4/sessions/$SESSION_ID" \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY"
```

Returns `204`. The session disappears from lists and cannot be opened or
continued. An active run and any pending queued messages are cancelled first.
Deleting again also returns `204`. On `502` or `503` the session was not
deleted; retry. Delete hides the session but keeps its records for billing; it
does not erase data.

### Share a read-only link

```bash
curl -X POST "https://api.browser-use.com/api/v4/sessions/$SESSION_ID/share" \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY"
```

The response contains `shareUrl`, `shareToken`, `isActive`, and `viewCount`.
Anyone with the link can see the session's tasks, results, workspace files, and
recording without an API key.

Disable the link with `PUT /api/v4/sessions/{id}/share` and
`{"isActive": false}`; it stops working immediately. Enabling it again keeps
the same URL. `GET /api/v4/sessions/{id}/share` returns `null` if the session
was never shared. Zero Data Retention projects cannot share sessions.

### Purge data (Zero Data Retention projects)

```bash
curl -i -X POST "https://api.browser-use.com/api/v4/sessions/$SESSION_ID/purge" \
  -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY"
```

Purge erases the session's run content, workspace files, recordings, and
downloads. It returns `204` when done, or `202` with `Retry-After: 60` while
active work or uploads delay deletion; call it again after that delay. Projects
without Zero Data Retention get `403`. The SDK `sessions.purge` helpers do not
handle the `202` yet, so use the HTTP call to know when deletion finished.
